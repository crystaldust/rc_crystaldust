# 01 · 评估清单与决策规则

> 本文件在任何候选方案打分之前编写并单独提交，决策规则锁定后不得事后调整。
> 需求来源：`.claude/PRPs/prds/message-hub.prd.md`（Core Capabilities MoSCoW、Technical Approach）。

## 评估对象

| 候选 | 版本（钉死） | 语言 / License |
|---|---|---|
| Hookdeck Outpost | `v1.7.0` | Go / Apache-2.0 |
| Svix server（含 Bridge） | `server-v1.102.1` | Rust / MIT |

**排除项**（不做深入评估）：
- **Convoy**：据第三方对比页称已转为副业维护，不建议生产使用（该说法来自厂商对比页，未核实；即便核实为误，其模型与 Outpost 同类，评估 Outpost 可覆盖同类结论）
- **Hook0**：定位小规模、低流量场景，与"规模可扩展"约束不符

## 评分标准（SCORING_SCALE）

| 分值 | 含义 |
|---|---|
| 3 | 原生支持，配置即可 |
| 2 | 通过官方扩展点 / 插件支持，无需改核心代码 |
| 1 | 需要修改核心代码才能支持（fork 并长期维护分叉） |
| 0 | 与其模型冲突，或实现成本接近重写 |

**证据格式（EVIDENCE_CITATION）**，以下三种之一：
- 源码：`outpost@v1.7.0:internal/deliverymq/xxx.go:L10-L40`
- 文档：URL + 章节名
- 实测：`docs/spike/04-poc-results.md#S3`

没有证据的结论标记为 `UNVERIFIED`，按 0 分计入加权得分，并在结论中单独列出。这样处理偏保守，避免靠推测拉高分数。

**满分** = 3 × 13（C1–C11、C17、C18）+ 2 × 4（C12–C15）+ 1 × 1（C16）= 39 + 8 + 1 = **48 个权重单位**。
**加权得分** = Σ(分值 × 权重)；**满分为 48 × 3 = 144**。

### 评分注意事项

- PRD 中标为 Won't 的能力（脚本 / DSL 转换引擎、端到端 exactly-once、业务方指定目标地址、终态回调 push、多区域部署）**不能成为加分项**。例如 Svix Bridge 的 JS 转换不能用来给 C3 加分
- 面向"SaaS 推送给客户"的能力（多租户 portal、Standard Webhooks 签名、客户自助订阅）与本场景无关，**不加分**
- C4 中的"自定义签名"指按供应商要求的签名方式（如对 Body 做 HMAC 后放入指定 Header），不是 Standard Webhooks 签名

## 决策规则（锁定）

**选择"二次开发"**，需同时满足以下条件：
1. 候选方案能力加权得分 ≥ 满分的 70%（即 ≥ 100.8，取 ≥ 101）
2. C3、C4、C5 三项中没有任何一项得 0 分
3. 所有得 1 分的项，所需改动集中在 ≤ 3 个核心模块（按顶层包 / crate 模块计）

**否则选择"自建"**，并在 ADR-0001 中列出可借鉴的设计（模块名 + 源码位置 + 借鉴什么）。

**两个候选都满足**时，取加权得分高者；得分差距 < 5%（< 7.2 分）时，取 N3 更优者。

**PoC 与源码证据冲突**时，以实测为准，并在评估文档中注明冲突。
